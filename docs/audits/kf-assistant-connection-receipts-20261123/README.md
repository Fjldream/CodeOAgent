# 按计算工程别名核对开发态与运行态连接

从开发态原生「测试连接」取得 KF 返回码，从目标计算 App 的一次请求取得读取码和实际业务行。每条回执标出测试时间、工程别名、证据来源，以及它与最近一次核对的保存配置是否一致。助手只读；开发人员决定何时改连接、重新发布或调用业务脚本。

## 在原对话查看

1. 在本机 M6 用原普通账号登录，打开「计算管理 → 默认工程组 → 测试工程-25 → 数据源管理」。
2. 打开「开发助手」，切到「园区能源总览 → 第一段对话」。工程入口决定查询范围，对话决定可用的回执。
3. 打开「工程工具 → 数据源连接回执」，工程连接别名填 `ArchiveRead`，点「查询」。应看到开发态返回码 0；运行态有一行 `{"batch":"B42","reading":506}`。展开工具内的列表可查看此前的 318 与失败记录，各行附取证时间。
4. 要取得新开发态回执，保持这段对话打开，在「数据源管理」的对应行点「测试连接」，完成后再查。要取得新 App 回执，打开目标请求式计算脚本，点「询问此脚本 → 工程工具 → 计算脚本回读 → 查询」。选择目标 App，填写同一别名，点「关联一次请求回包」。通过正常业务入口调用一次，导出本次含响应正文的浏览器 HAR，在十分钟内选入。浏览器在本机提取该次调用，发送剔除认证字段的业务观察结果。
5. 也可在该工程的原对话提问「请核对 ArchiveRead 最近一次开发态测试和目标 App 的实际读数，给出时间，并把历史结果单列。」本次现场验收走普通账号浏览器中的工程工具，自由问答的云端措辞未复测。

现场失败阶段，验收脚本首次把原生错误 HTTP 状态当成了用例中断。保留当次真实失败记录，改正验收脚本的断言并重测，留下两条开发态失败回执。首次停止 App 的运维命令等待超时，复查仍显示运行，重试后收到停止、快速部署、启动三步回执，再采集 B 的读数。两次调整均限于验收操作。迁入本机 M6 的 7 条回执均属于同一开发者、原对话、新工程和别名；试点原有 13 轮对话、方案版本和既有计算及报表回执通过摘要复核。

## 工程适用范围

- 助手按账号权限重读当前工程和可见平台源。原生测试只记按钮实际收到的返回码；不支持、超时等状态应显示为未核实。数据库失败时的 -1 是本次请求脚本的业务读取码，其他脚本可返回自己的错误码。
- 运行态取证要求保存脚本含有指向该别名的可解析 KC 读取调用，目标 App 的实际回包提供 `OutParam.connectionRead` 的 `alias`、整数 `code` 和数组 `rows`。已有任意 JSON 回包或仅有周期脚本的工程仍需提供相应的读取证据。只做读取的验收脚本适合复测。字段来自业务回包，无法借此独立证明每一行的内部生成过程。
- 工具重新核对连接指纹和已观察的配置代次，按 App 分别标记历史；在取证窗口内观察到配置变化会拒收。KF 未提供完整的配置变更流水。两次观察之间改动又原样还原且无版本字段时无法识别。结果描述的是取证时刻，部署版本需要部署回执和实际业务结果另行核对。
- 本次实机覆盖 PostgreSQL 和请求式计算 App。可在其他计算工程复用相同的记录机制；其他数据库、适配器与周期读取路径的实机覆盖分开登记。独立数据库运行在本次验收的开发机，复测新读数时须保持开发机和数据库在线，已保存的回执可在试点查看。
