# 从方案引用进入计算脚本开发

从原方案对话提出计算需求。助手按本账号重新检查上次总览及其关联工程的权限，回读当前保存的连接、点读写属性、计算工程词典与启用函数。旧版总览可用原入口重建引用。多个可用计算工程无法唯一确定时，开发人员可以直接打开要承载脚本的工程，在原对话继续。

准备工具提供匿名绑定与已观察到的读写方向。工程对象的选取、脚本宿主、业务口径及尚须明确的问题存于本账号的当前对话。口径明确后，在紧接的回复中输入“确认生成”。提交前再次读取工程配置，核对目标、绑定指纹、读写属性、函数签名与已确认的宿主；通过 KF 静态检查的完整 JS 才进入脚本交付。正式方案清单仍通过原有的单独提议与确认流程更新。

首版 ce8f8b5186cd 通过 149 项开发版及 19 项试点回归。现场题“可用容量百分比”在原普通账号对话中让模型读取了引用并调用了口径核对。编排额外调用输入输出、工程配置和运行接口查询，用完五次外部请求后未能交付追问，首版未通过。失败回执

修订版 0dee151ecc5b 在取得方案绑定后只开放当前阶段的工具。模型提交并通过核对的口径或 JS，可以在当前 OpenCode 会话内交付，省去让云模型重述同一条材料的请求。已通过 150 项开发回归及 20 项试点回归后冻结。独立题另取模块组数向上取整与零需求备用口径，测试项目自带一个单参进位函数和结果缓存。完整生成与运行回执需在原对话中复验。冻结记录

### 独立验收结果

冻结版 `0dee151ecc5b` 未通过。普通开发账号在原对话从计算工程提出模块组数需求，再从关联数采工程补充零需求取零组。两轮都找到了画面读取的业务点与单参进位函数，也都把指定缓存列成输入、把系统年份变量列成输出。

第三轮按模型追问补明写缓存失败时返回 null，并再次点名首轮指定的结果缓存、说明只需生成请求式脚本。回复文字写了“仅 request”，结构化清单仍登记 request 和 customFunction，输出仍是系统年份变量。验收停在开发人员确认处。目标独立 App 的请求列表只有基线观察脚本，HTTP 200 读回缓存 0。正式清单版本与提议摘要以及本轮之前的历史均已复核。脚本保存、业务回包和写回尚无验收结果。M6 脚本与导航联合发布暂缓。逐轮回执

在源码中，`approvedBindings` 检查引用归属和种类，对点位校验读写方向，对工程变量仅校验其为有效变量。口径工具允许用户点名的变量与模型选作输出的变量不同，也允许把复用函数记为另一个待生成宿主。后续版本优先在确认前核对这些约束，为模型返回可自行修正的诊断，并在异名、不同宿主的通用回归中验证。
